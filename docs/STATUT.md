### Anti-écrasement des fiches (décision 5 de Greg, 2026-11-04)

- **Principe** : à l'ouverture d'une fiche (élément ou projet), on garde sa version (`updated_at`). À l'enregistrement, la mise à jour ne passe que si la ligne n'a pas changé depuis (`UPDATE … WHERE id = … AND updated_at = …`, une seule requête : c'est la base qui tranche, aucune course possible). Sinon : rien n'est modifié, message « Cette fiche a été modifiée par quelqu'un d'autre depuis son ouverture. Elle vient d'être rechargée : rouvre-la, regarde ses changements, puis refais ta modification. », la fiche se ferme et les données se rechargent (sinon la fiche rouverte montrerait la même version périmée). Une fiche supprimée entre-temps le dit aussi.
- **Pas de migration** : le mécanisme est dans l'application (`updateIfUnchanged`) ; la base fournit déjà `updated_at`, mis à jour à chaque modification.
- **Cas particulier** : une dépendance ajoutée ou retirée depuis la fiche modifie l'élément elle-même ; au prochain enregistrement la fiche repart de la version rechargée (petite fenêtre où une modification extérieure simultanée ne serait pas détectée).
- **Limites assumées** : ne protège que les enregistrements par les fiches (pas les gestes du Gantt : glisser, redimensionner, « placer » — ils écrivent seulement des dates et rendent la fiche déjà ouverte périmée, ce qui est détecté) ; l'API directe reste « dernier gagnant, champ par champ ».
- **Vérifié** : types, lint ; dans une page de test isolée avec une base simulée : requête envoyée avec la bonne version, conflit → message + fermeture + rechargement, succès → « Projet modifié », fiche supprimée → message dédié. **Pas vérifié sur la vraie base** : étape `U5c-conflit` ajoutée à `e2e-gantt` (deux sessions réelles ; 44 étapes attendues), non exécutée.
